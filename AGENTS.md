# AGENTS.md - cbl-api-gateway

Периметр платформы: TLS (вне сервиса), аутентификация мерчантов по кэшу проверки,
rate limit, маршрутизация /v1 и /admin/v1.

Обязательные глобальные правила: `../../AGENTS.md`, `../../.specs/CBL-001-development-process.md`,
`../../.specs/CBL-002-repos-and-docker.md`, контракты `../../.specs/CBL-003-contracts.md`.
Длинное тире (U+2014) запрещено, используется только дефис.

## 1. Границы

In scope: reverse proxy `/v1/**` в Billing API и `/admin/v1/**` в Back-office; контроль
API-ключа по общему с 7.2 Redis-кэшу (deny - мгновенный 401, промах - делегирование BFF);
лимит запросов на мерчанта и группу маршрута; problem+json ответы периметра (401/404/429/503).

Out of scope: TLS-терминация (LB/инфраструктура, 0.6); RBAC и лимиты операторов `/admin/v1`
(12.x); источник истины проверки ключей (Billing API, 7.2); предел тела запроса (Billing API,
7.3); метрики Prometheus (0.7); L3/L4-защита (инфраструктура).

## 2. Контракты

- REST входящий: `/v1/**` (мерчант, Bearer + лимит), `/admin/v1/**` (оператор, без лимита
  периметра), `/healthz`, `/readyz`; ошибки - `application/problem+json` (RFC 9457):
  401 `unauthorized` (`WWW-Authenticate: Bearer realm="billing"`), 429 `rate_limited`
  (`Retry-After`), 503 `service_unavailable` (`Retry-After: 1`), 404 `not_found`.
- REST исходящий: проксирование на `BILLING_API_URL` и `BACKOFFICE_URL` (http/https без
  userinfo/query), тело стримится без буферизации, `X-Request-Id` сквозной (клиентский
  вне формы `[A-Za-z0-9._-]{8,64}` заменяется сгенерированным), входящие
  `X-Forwarded-*`/`Forwarded`/`X-Real-IP` удаляются до `SetXForwarded` - апстрим видит
  только канонические значения периметра.
- gRPC, Kafka: отсутствуют.
- Хранилище: Redis - чтение `apikey:v1:{hex sha256}` (пишет Billing API, контракт 7.2 FR-6),
  счетчики `rl:{merchant|token:hex}:{route}:{window}` (CBL-003 раздел 7, TTL 2 окна, Lua
  INCR+PEXPIRE). Своих таблиц и миграций нет.

Спека задачи: `.specs/CBL-7.5-rate-limit.md`; контракт - `cbl-protos@cf-3.1` (семантика
`429`/`Retry-After`/Problem), `CBL-003` §7.

## 3. Архитектура

Слои: `internal/transport` (router, proxy, httpmw) -> `internal/usecase` (Perimeter,
FallbackCounter) -> `internal/domain` (Bearer, TokenHash, RouteGroup, IdentityKey,
RateLimitKey, ParseKeyCacheValue) -> `internal/storage` (RedisStore, LocalLimiter).

Ключевые решения: лимит - фиксированное окно 1 с, выровненное по Unix-секунде, ключ по
`CBL-003`; при промахе кэша ключа идентификатор лимита `token:{hex}` (не IP); при ошибке
Redis - предохранитель на 1 с и локальный in-process счетчик (деградация, не отказ;
журнал троттлится 5 с, отмена клиента не взводит предохранитель); апстрим получает свой
Host; `proxyWriter` скрывает `CloseNotify` gin от `httputil.ReverseProxy` (тот паникует на
несовместимых Writer), отмена отслеживается контекстом запроса; заголовок ответа
`X-Request-Id` не дублируется (заголовок периметра снимается перед копированием ответа).

## 5. Порты и окружение

HTTP `8000`, gRPC `-`, метрики `9200`.
Переменные (применимые к сервису): `HTTP_ADDR`, `METRICS_ADDR`, `BILLING_API_URL`
(по умолчанию `http://localhost:8010`), `BACKOFFICE_URL` (`http://localhost:8020`),
`RATE_LIMIT_PER_SEC` (целое > 0, по умолчанию 100; невалидное - отказ старта),
`UPSTREAM_TIMEOUT` (1s - 60s, 10s), `REDIS_ADDR` (опционален: без него лимиты
только локальные, WARN; контроль ключа уходит в BFF). Невалидные URL апстримов
(не http/https, без хоста) - отказ старта.

## 6. Правила разработки

- Конвейер: SDD-спека в `.specs/` -> архитектура -> контракты -> тесты вперед -> код ->
  ревью 4 агентами (без контекста, архитектура, контекст, безопасность - блокирующий) ->
  AGENTS.md -> финальные прогоны -> линтеры -> коммит.
- Покрытие unit+integration не ниже 80%; локальный e2e в docker-compose обязателен.
- Ключ и токены не логируются; значения `deny` и `ok:<merchant>` кэша - якорь доверия
  авторизации (KI-api-gateway-02); наружу не отдаются детали апстримов и Redis.
- Docstring на русском в стиле godoc (первая строка с имени сущности, точка в конце);
  комментарии объясняют почему; ошибки через `%w`; панки в бизнес-коде запрещены.
- Коммит: `CBL-<эпик>.<номер>: <краткое сообщение>`, спека с тем же префиксом в том же коммите.

## 7. SLO и метрики

SLO уточняется в задаче 14.4. Горячий путь: P95 накладных расходов периметра менее 5 мс;
входная нагрузка до 3000 RPS (14.2). Базовые метрики после 0.7: доля 429, hit/miss
кэша ключей, доля fallback-лимита и анонимного трафика (KI-api-gateway-07), latency
p95/p99, доля ошибок апстримов.

## 8. Trade-offs

| ID | Решение | Плюсы | Минусы и компенсация |
| :-- | :-- | :-- | :-- |
| T-GW-01 | Контроль ключа на периметре читает `apikey:v1:*` (7.2): deny - 401 без апстрима, промах и ошибка Redis делегируют решение BFF | периметр не авторитетен, источник истины один; горячий путь без БД | холодные ключи и недоступный Redis стоят похода в BFF; запись в Redis = имперсонация | ACL/сеть до prod (0.6, KI-api-gateway-02); tombstone deny; BFF всегда перепроверяет ключ (defense in depth) |
| T-GW-02 | Лимит - фиксированное окно 1 с (`rl:{identity}:{route}:{window}=номер секунды`), счет Lua INCR+PEXPIRE в Redis | ключи контракта CBL-003, атомарность, нет состояния клиента, счетчики не утекают | нет burst-толерантности; на границе секунды возможно 2x лимита | калибровка в 14.1; лимит конфигурируем; burst допускается осознанно (S-размер) |
| T-GW-03 | Идентификатор лимита промаха - `token:{hex sha256}` | NAT-адреса мерчантов не штрафуют друг друга; случайные токены атакующего получают независимые корзины | распределенный перебор множеством токенов и дробление квоты по группам маршрутов умножают поток к BFF/PG; анонимный трафик периметром не ограничен глобально | KI-api-gateway-07; глобальные пики ограничиваются инфраструктурой и профилем 14.2; доля анонимного трафика - метрика 0.7; per-merchant конфигурация 12.x |
| T-GW-04 | При отказе Redis - предохранитель на 1 с и локальный in-process лимитер инстанса (T-11) | периметр не отказывает в обслуживании; первая ошибка стоит до ~1 с (две попытки таймаутов 200/300 мс), далее Redis не опрашивается; журнал деградации троттлится | у многорепличного деплоя эффективный лимит умножается на число реплик; точность падает | короткие окна; метрика fallback (0.7); калибровка 14.x; KI-api-gateway-05 |
| T-GW-05 | `/admin/v1` проксируется без лимита мерчанта и без проверки токена на периметре | RBAC и аудит - зона Back-office (12.1), нет дублирования | периметр не защищает операторский контур от всплесков | лимиты/RBAC операторов - 12.x (KI-api-gateway-04); admin не публикуется мерчантам |
| T-GW-06 | TLS-терминация вне сервиса (LB/ingress, 0.6) | сервис без сертификатов и TLS-конфигурации | локальный стенд http; ошибки TLS выглядят как отказ соединения | prod-схема описана в CBL-002 §7; loopback-only стенд |
| T-GW-07 | Reverse proxy на `httputil.ReverseProxy` с `Rewrite` (Go 1.26 депрецировал Director) и оберткой `proxyWriter` | стриминг без буферизации, канонические X-Forwarded-*, отмена по контексту; нет паники gin CloseNotify на несовместимых Writer | нестандартная обертка требует сопровождения; `Unwrap()` не реализован (ResponseController-пути вроде Hijack не поддержаны, пока не требуются) | SSE-стриминг и Flush покрыты тестом; unit/integration тесты цепочки |

## 11. Runbook

Периметр (CBL-7.5):

1. Массовые 429: проверить `RATE_LIMIT_PER_SEC`, группу маршрута в ключе `rl:*`
   (run: `docker compose exec redis redis-cli --scan --pattern "rl:*"`), всплеск мерчанта;
   при легитимном росте - поднять лимит и перезапустить сервис (лимит из env).
2. Рост 401: проверить tombstone (`GET apikey:v1:<sha256>` = deny) и отзыв/ротацию ключа
   (шаги Billing API 7.2); пустой `Authorization` у клиента.
3. 503 на апстриме: проверить `BILLING_API_URL`/`BACKOFFICE_URL`, доступность сервисов,
   логи периметра `upstream request failed` (детали только там); клиенту приходит
   `Retry-After: 1`.
4. Redis недоступен: периметр деградирует к локальным лимитам (WARN
   `rate counter degraded to local limiter`), проверка ключей уходит в BFF; приоритет -
   восстановление Redis, лимиты при нескольких репликах перестают быть общими
   (KI-api-gateway-05).
5. Подозрение на подмену Redis (KI-api-gateway-02): сверить ключи кэша через Billing API
   (`keyctl verify`), отозвать и перевыпустить затронутые ключи, разобрать доступ; денежные
   исправления - только сторно (10.x).
6. Диагностика лимитов: ключ окна - `rl:{merchant|token:hex}:{route}:{window}`, TTL 2 с;
   счетчик можно посмотреть `redis-cli GET <ключ>`, окна различаются номером Unix-секунды.
7. Диагностика маршрутизации: периметр не читает тело и не кэширует ответы; сверить
   `X-Request-Id` периметра и апстрима в логах обоих сервисов.
