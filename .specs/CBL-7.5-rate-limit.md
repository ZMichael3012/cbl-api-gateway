# CBL-7.5. Rate limiting на периметре и маршрутизация /v1 и /admin/v1

| Поле | Значение |
| :-- | :-- |
| Эпик | E7, `Billing API и Gateway` |
| Репозиторий | `cbl-api-gateway` |
| Размер | S |
| Волна и параллельная группа | W3-BILLING |
| Зависит от | `CBL-7.2` (контракт кэша проверки ключей FR-6), `CBL-7.1` (Problem, `429`, `Retry-After`) |
| Версия контрактов | `cbl-protos@cf-3.1` (семантика `429`), `CBL-003` §7 |
| Статус | done, ревью закрыто |

## 1. Контекст и цель

`CBL-000`: `cbl-api-gateway` - периметр платформы: TLS, аутентификация, rate limit,
маршрутизация; основной маршрут `Мерчант -> API Gateway -> Billing API -> доменные сервисы`.
Задача 7.5 делает гейтвей работающим прокси с лимитами: маршрутизация `/v1` в Billing API и
`/admin/v1` в Back-office, контроль ключей по общему с 7.2 Redis-контракту (периметр читает
`apikey:v1:*` и отсекает `deny` без похода в BFF), лимит запросов на мерчанта.

Ограничения по безотказности: входная нагрузка до 3000 RPS, пики 1.5x - 2x (`CBL-000`);
`CBL-002` §8 - `billing-api` 1000 RPS чтения, `429` только при превышении лимита. Trade-off
T-11: лимиты в Redis быстрые, но при потере данных возможны ложные решения; потеря Redis не
должна превращаться в отказ обслуживания (деградация с локальным лимитом, T-02/T-11).
Контракты ответов (Problem RFC 9457, `429` с `Retry-After`, `rate_limited`) заморожены 7.1.

## 2. Границы

In scope:

- reverse proxy `/v1/**` -> Billing API, `/admin/v1/**` -> Back-office (стриминг тела);
- контроль ключа на периметре: строгий Bearer, sha256, чтение `apikey:v1:*`,
  немедленный `401` на `deny`, промах - делегирование BFF (источник истины 7.2);
- лимит запросов на мерчанта на маршрут в Redis (`rl:...`) с локальным fallback;
- ответы `429 rate_limited` и `503 service_unavailable` в формате контракта;
- сквозной `X-Request-Id` от периметра до апстрима;
- e2e compose: redis + stub-апстрим + гейтвей.

Out of scope: TLS-терминация (инфраструктура, 0.6 и prod-LB); RBAC и лимиты операторов
(`/admin/v1`, 12.x); конфигурация лимитов на мерчанта (12.x); источник истины проверки
ключей (BFF, 7.2); предел тела запроса (BFF, 7.3); метрики Prometheus (0.7); нагрузочный
профиль k6 (14.1/14.2, KI); аппаратная защита от L3/L4-флуда (инфраструктура).

## 3. Функциональные требования

FR-1. Маршрутизация: `Any /v1` и `/v1/*path` -> `BILLING_API_URL`,
`Any /admin/v1` и `/admin/v1/*path` -> `BACKOFFICE_URL` через `httputil.ReverseProxy`
(тело стримится, без буферизации); статус, заголовки и тело ответа апстрима сохраняются;
`X-Request-Id` периметра передается апстриму; сбой апстрима - `503 application/problem+json`
`service_unavailable` с `Retry-After: 1` (семантика 7.1), детали ошибки только в лог;
неизвестный путь - `404` problem+json `not_found`. Редиректы Gin по умолчанию отключены
(`RedirectTrailingSlash`, `RedirectFixedPath`), иначе POST теряет тело на 301.

FR-2. Контроль ключа (совместно с 7.2 FR-6): ровно один заголовок `Authorization`, схема
`Bearer` регистронезависима, токен без пробелов; нарушение формы - `401` без обращения к
Redis. Далее sha256(токен) hex и `GET apikey:v1:<hex>`: `deny` - немедленный `401`
(WWW-Authenticate, как 7.2); `ok:<merchant_id>` - мерчант становится идентификатором
запроса (формат merchant_id - как в 7.2: `[A-Za-z0-9_-]{1,128}`, не только UUID); промах,
ошибка Redis или испорченное значение - запрос уходит в BFF (он проверяет источник истины
и заполняет кэш), но получает идентификатор промаха для лимита. Ключ никогда не логируется.

FR-3. Лимит на мерчанта: идентификатор запроса - merchant_id (кэш-хит) или
`token:<hex sha256>` (промах); ключ счетчика `rl:{identity}:{route}:{window}` по `CBL-003`
§7. Окно фиксированное, 1 секунда, выровнено по Unix-секунде (`window` - номер секунды);
`route` - первый сегмент пути после `/v1/`, нормализуется до `[a-z0-9-]{1,32}`, иначе
`other`, пустой - `root`; `/admin/v1` не лимитируется в 7.5 (12.x). Счет атомарный:
Lua `INCR` + `PEXPIRE` (TTL 2 окна; TTL ставится и ключу, созданному извне без TTL).
Превышение `RATE_LIMIT_PER_SEC` (по умолчанию 100) - `429 application/problem+json` код
`rate_limited`, `Retry-After: <ceil(остаток окна)>` (минимум 1), апстрим не вызывается.
Заголовки `X-RateLimit-*` контрактом 7.1 не предусмотрены - не добавляются (аддитивно позже).

FR-4. Деградация: первая ошибка Redis взводит предохранитель на 1 секунду (запросы в
окне не платят таймауты клиента), счет ведет in-process fallback-лимитер того же окна и
лимита (на инстанс; при нескольких репликах эффективный лимит умножается, trade-off);
пустой `REDIS_ADDR` - старт в локальном режиме с WARN. Журнал деградации троттлится
(не чаще раза в 5 с); отмена клиента не считается сбоем зависимости. Локальный лимитер
не может отказать в обслуживании: его сбой (недостижим кроме паники) трактуется как
пропуск с WARN - контроль ключа при этом всегда остается за BFF (fail-safe 7.2).

FR-5. Health: `/healthz` - liveliness; `/readyz` - сервис готов обслуживать трафик (Redis
опционален, деградация задокументирована), проверяет только собственный процесс.

FR-6. Конфигурация fail-fast (невалидное значение - отказ старта): `BILLING_API_URL`
(`http(s)://` без userinfo/query/fragment, по умолчанию `http://localhost:8010`),
`BACKOFFICE_URL` (`http://localhost:8020`), `RATE_LIMIT_PER_SEC` (целое > 0, 100),
`UPSTREAM_TIMEOUT` (1s - 60s, 10s - `ResponseHeaderTimeout` транспорта; серверный
`WriteTimeout` выводится как бюджет + 5s, иначе стриминг и контрактный 503 обрывались бы
раньше), `REDIS_ADDR` (опционален); `HTTP_ADDR` (:8000), `METRICS_ADDR` (:9200).
Redis-клиент - короткие таймауты как 7.2 (dial 200 мс, read/write 300 мс, MaxRetries 1).
Сбой листенера HTTP/метрик завершает процесс ненулевым кодом (оркестратор видит отказ).

## 4. Контракты

REST (внешний вид ошибок периметра повторяет контракт Billing API `cbl-protos@cf-3.1`):

- `401` - Problem `code=unauthorized`, `WWW-Authenticate: Bearer realm="billing"`;
- `429` - Problem `code=rate_limited`, `Retry-After` (компонент `RateLimited`);
- `503` - Problem `code=service_unavailable`, `Retry-After: 1`;
- `404` - Problem `code=not_found`.

Redis (владелец ключей - API Gateway; `CBL-003` §7):

| Ключ | Значение | TTL | Чтение/запись |
| :-- | :-- | :-- | :-- |
| `rl:{merchant}:{route}:{window}` | счетчик окна (строка целого) | 2 окна | только Gateway |
| `rl:token:{hex sha256}:{route}:{window}` | счетчик промаха кэша ключей | 2 окна | только Gateway |
| `apikey:v1:{hex sha256}` | `ok:{merchant_id}` или `deny` | 7.2 | пишет Billing API, читает Gateway |

Upstream: HTTP REST (`/v1` BFF, `/admin/v1` Back-office); gRPC и Kafka у периметра нет.
Собственные RPC/топики не добавляются.

## 5. Модель данных и миграции

Своих таблиц и миграций нет: состояние лимитов - Redis (эфемерное, потеря допустима,
T-11); источник истины авторизации - PostgreSQL Billing API (7.2). Путь `readyz` БД не

## 6. Правила идентификации и решения

Матрица контроля ключа:

| Состояние `apikey:v1` | Действие | Идентификатор лимита |
| :-- | :-- | :-- |
| `deny` | `401` немедленно, апстрим не вызывается | - (лимит не расходуется) |
| `ok:<merchant_id>` (формат 7.2: `[A-Za-z0-9_-]{1,128}`) | проксирование | merchant_id |
| промах | проксирование (BFF проверит и заполнит кэш) | `token:<hex>` |
| ошибка/порча значения | проксирование + WARN (троттлинг 5 с) | `token:<hex>` |

Матрица лимита: `count <= limit` - проксирование; `count > limit` - `429`, апстрим не
вызывается; ошибка Redis - локальный счетчик и решение по нему. Смена идентификатора в
середине окна (первый запрос с холодным кэшем, затем хиты) расходует разные корзины -
суммарный всплеск не более 2x лимита в секунду перехода, безопасно и документировано.

## 7. Edge cases

Дубли `Authorization` и токен с пробелами - `401` без обращения к Redis (как 7.2);
значение кэша с испорченным merchant_id - режим промаха + WARN (подмена значения не
повышает прав, лимит по токену, формат идентификатора не позволяет выйти за пространство
ключей `rl:`); `Retry-After` не меньше 1 секунды; лимит 1 и окно на границе секунды (счет
нового окна начинается с 1; тесты отправляют запросы до отказа, а не полагаются на номер
окна); `route` длиннее 32 символов или не из `[a-z0-9-]` - `other`; пути `/v1` и `/v1/` без
сегментов - `root`; запросы без пути после префикса - апстрим получает путь как есть;
ключ, созданный вне сервиса без TTL, получает TTL первым инкрементом; клиентский
`X-Request-Id` вне формы `[A-Za-z0-9._-]{8,64}` заменяется сгенерированным (подмена
корреляции логов); входящие `X-Forwarded-*`/`Forwarded`/`X-Real-IP` удаляются до
`SetXForwarded` (спуфинг клиентских IP в BFF невозможен); сбой апстрима - `503` без
деталей наружу; отмена клиента прерывает проксирование (контекст запроса) и не считается
сбоем зависимости; `Expect: 100-continue` и чанковые тела проходят стримингом; дубль
`X-Request-Id` в ответе не возникает (заголовок периметра снимается перед копированием
ответа апстрима).

## 8. Нефункциональные требования

Бюджет задержек: горячий путь хитов - `GET` + `EVAL` в Redis (менее 1 мс локально), P95
накладных расходов периметра менее 5 мс; 3000 RPS и пики - на глобальном профиле (14.2),
стартовый порог лимита 100 rps на мерчанта и маршрут калибруется в 14.1. Отказ
зависимости: Redis - первая ошибка стоит до ~1 с (две попытки таймаутов 200/300 мс),
предохранитель на 1 с переключает на локальный лимитер без обращения к Redis (T-11,
троттлинг журнала 5 с, отмена клиента не взводит предохранитель); BFF - `503` с
`Retry-After`; серверный `WriteTimeout` выводится из бюджета апстрима с запасом.
Безопасность: ключ не логируется (AccessLog не пишет заголовки); значение `deny`
доверенное наравне с записью Redis (KI-billing-api-02, ACL 0.6); URL апстримов только из
конфигурации без userinfo/query (SSRF через заголовки невозможен - прокси не читает
`X-Forwarded-Host` и сам формирует канонические `X-Forwarded-*`); стенд публикует порты
только на loopback; наружу не отдаются детали апстрима и Redis.

## 10. Ревью (CBL-001, шаг 6)

Четыре независимых прохода (15.10.2026). BLOCKER закрыт: `ParseKeyCacheValue` требовал
UUID, но контракт 7.2 пишет merchant_id произвольной формы `[A-Za-z0-9_-]{1,128}` (ops-CLI
`m-1`, e2e billing-api `m-e2e`) - лимит на мерчанта фактически не работал, каждый хит шел
в корзину токена; заменено паттерном 7.2, добавлен регресс-тест `ok:m-1`. MAJOR закрыты: входящие
`X-Forwarded-*`/`Forwarded`/`X-Real-IP` удаляются до `SetXForwarded` (спуфинг IP в BFF);
предохранитель Redis (окно 1 с) убирает поток таймаутов при отказе, журнал деградации
троттлится, отмена клиента не классифицируется как сбой; `WriteTimeout` сервера выводится
из `UPSTREAM_TIMEOUT` (контрактный 503 не обрывался при бюджете до 60 с); сбой листенера
завершает процесс ненулевым кодом; тесты маппинга двух апстримов, потокового Flush,
`Expect: 100-continue`, санитизации идентификатора и TTL внешнего ключа добавлены;
шардинг квот по route и анонимный поток зафиксированы KI-api-gateway-07; дублирование
401/Bearer с BFF - KI-api-gateway-06. MINOR/NIT закрыты: loopback-публикация портов
стенда, запрет userinfo/query в URL апстримов, `TLSHandshakeTimeout`, `PTTL`-проверка в
Lua, дубль `X-Request-Id` в ответе исключен, тесты не зависят от границы окна, `/healthz`
в e2e, `make up` поднимает профиль app. Принято осознанно: `ErrAbortHandler` штатных
обрывов клиента логируется ginmw.Recovery как паника (KI-api-gateway-08, правка cbl-kit
отдельной задачей); базовые образы без digest (платформенная практика, 0.2).

## 12. Открытые вопросы и решения

Решения (ADR-стиль):

- Фиксированное окно вместо token bucket: детерминированные ключи `{window}` из `CBL-003`,
  атомарный Lua, отсутствие состояния клиента; отсутствие burst-толерантности принято
  (лимит калибруется в 14.1).
- Идентификатор промаха `token:<hex>` вместо IP: NAT-адреса мерчантов не штрафуют друг
  друга, случайные токены атакующего получают независимые корзины; IP-лимит оставлен
  инфраструктуре.
- Промах кэша проксируется, а не отвергается: источник истины - BFF (7.2), периметр не
  может выносить авторитетных решений о ключе по промаху; цена - редкие холодные ключи
  доходят до BFF.
- Локальный fallback при отказе Redis: доступность важнее точности (T-11), множитель
  лимита на число реплик компенсируется короткими окнами и калибровкой; предохранитель
  на 1 с и троттлинг журнала сохраняют бюджет деградации честным.
- TLS-терминация на периметре не реализуется в 7.5: локальный стенд без TLS, prod -
  LB/ingress (0.6); собственный TLS-листенер при необходимости - отдельная задача.
- `ErrAbortHandler` штатных обрывов клиента логируется `ginmw.Recovery` как паника:
  правка библиотеки - отдельной задачей cbl-kit (KI-api-gateway-08), периметр не
  оборачивает Recovery повторно.
